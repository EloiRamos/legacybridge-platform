# Known limitations

Fictional engagement; HALDEN and SKARVIK are simulators. Who executed which
check is stated in [VERIFICATION](evidence/VERIFICATION.md#who-executed-what). Accepted or documented means known and tolerated, **not** remediated. Nothing here is production-ready.

## A. Limitations found or decided during implementation

| ID | Limitation | Where it matters | Status |
|---|---|---|---|
| L-01 | **Scanned 2026-11-25 (pip-audit 2.9.0, npm audit, Trivy 0.69.3 with that day's database):** Python and npm packages, none reported. App, migration and wire-tap images (Debian 13): 0 critical, 53 high, 76 medium, none with a fix, after the only fixable one (`libzstd1`, CVE-2026-124851) was updated. **Residual:** PostgreSQL 17 image: critical `libxml2` CVE-2026-6653 without a fix, and Go standard-library advisories (1 critical, CVE-2025-68121) in `gosu`, which only starts the server process; 99 high. HALDEN (Ubuntu 24.04, operating-system packages only): 2 high, 28 advisories fixable by a newer base. SKARVIK (Debian 12): 2 critical without a fix, 100 high. Both Dockerfiles are frozen. The Maven stage and the Java packages were scanned earlier (Guava in the build stage, 1 high). A scanner lists packages; reachability was not analysed one by one, and a clean scan is not absence of vulnerabilities | Image exposure beyond loopback; build-time trust | Own images updated; residuals accepted only for loopback use; the frozen bases are kept for this release |
| L-02 | Live OpenAI evidence is fixed, fictional scenarios on the only accepted model, `gpt-6-luna`: 104 requests on the previous version (2026-11-24: a smoke, 38 trials, two browser journeys) and 13 on this one (2026-11-25: a screenshot run, one browser validation, one truncated answer); reported identifier always `gpt-6-luna`, for tool calls, final answers and an incomplete answer ([results](evidence/VERIFICATION.md#assistant)). A genuine refusal by the model has not been observed live and is not provoked; it is tested with a mocked transport only, like provider outages, malformed JSON and model mismatches. Earlier runs on `gpt-6.1-terra` and `gpt-5.4-mini-2026-03-17` are history and say nothing about it. After a mismatch the process stops using the model until it is restarted; `/readyz` then reports `assistant: stopped:model-mismatch` and stays ready | Reliability of a real model, real data | Measured, not a reliability statement |
| L-03 | *Was:* `.env.example` listed `HALDEN_BASE_URL`, `HALDEN_TIMEOUT_SEC` and `SKARVIK_EXCHANGE_DIR`, which compose does not read, and compose did not pass `LBF_COOKIE_SECURE`. *Now:* every active `.env.example` line is consumed by `compose.yaml` (`LBF_HALDEN_URL`, `LBF_TRANSPORT_TIMEOUT_SEC`; the exchange directory is fixed at `/exchange`); `LBF_COOKIE_SECURE` and `LBF_PUBLIC_ORIGIN` are passed through with unchanged defaults; variables compose does not pass are commented out ([CONFIGURATION](operations/CONFIGURATION.md)) | Operator confusion | Remediated, `tests/security/test_env_contract.py`; reviewed |

Remaining: the **test profile** (`deploy/compose.test.yaml`) deliberately mounts the public fictional fixture `deploy/test-fixtures/halden_secret.txt` (the simulator's documented demo value), because the independent oracles and the resilience harness authenticate with it | Test-profile credential is public by design (fictional simulator, loopback/internal network only) | Remediated for `default`/`demo`; reviewed |
| L-05 | *Was:* no response size cap at the HALDEN transport. *Now:* every HALDEN response body is capped at 1 MiB in `CapturingTransport` (refused, never truncated; ADR-F09). Remaining: HALDEN XML is still parsed by the frozen bridge with the standard library, so entity expansion inside a body under the cap is not bounded | A hostile HALDEN could attempt entity expansion | Size cap remediated; XML parser accepted under the internal-system trust assumption |
| L-06 | Metric names differ from the first specification: the age of the oldest `UNKNOWN` is `lbf_unknown_age_max_seconds` (not `lbf_unknown_oldest_seconds`); `lbf_awaiting_ack_oldest_seconds` and `lbf_audit_head_seq` are **not** exported. Present: `lbf_operations{state}`, `lbf_transmissions_total{kind,observation}` (no `backend` label, unlike the first specification), `lbf_engine_leader`, `lbf_backend_up{backend}`, `lbf_acknowledgements_total`, `lbf_reconciliation_runs_total`, `lbf_operation_transitions_total`, inference metrics (OPS-02) | Monitoring dashboards built from the first specification | Documented |
| L-07 | *Was:* the secret scanner (`acceptance/secret_scan.py`) had no `OPENAI_API_KEY=` assignment pattern. *Now:* rule `openai-key-assignment` flags any literal value of 8+ characters assigned to `OPENAI_API_KEY` (`=`/`:`, quoted or not), whatever its prefix; references, empty values, placeholders and short documentation examples are not flagged | A placeholder-like real value (e.g. one starting with `example`) would be missed | Remediated, `tests/unit/test_secret_scan_patterns.py`; reviewed |
| L-08 | Clean-clone deployment was timed only with cached image layers: 19 s through `make demo-up` on this version (16.6 s through the default commands on an earlier one) | First-install time on a new host is minutes | Documented |

Refusing a second start while the first is still running looks the same | Owner-run live runs | By design: nothing continues without a resolved end |

| L-19 | The smoke authorization fields `max_trials` and `max_input_tokens` are declared but **not enforced** by the smoke; `approved_by`/`approved_at` are recorded, not validated | Misreading them as controls | Documented |

| L-33 | A draft is written directly only when the whole message is a drafting command of a narrow English grammar (digits or number words up to ninety-nine, plain unit words, identifiers as written, no quotation, question, condition or second order). | L-34 | A pending proposal lives in process memory, ten minutes, one per session; a newer one replaces it, and a restart loses it. | L-39 | Assistant proposals live in process memory for ten minutes, per person and session; a restart discards them (nothing was written) | Assistant drafting | By design |

## B. Residual risks

| Risk | Residual risk |
|---|---|
| RK-01 Non-idempotent backend writes | Duplicates created outside the console (direct HALDEN entry) are not prevented; a HALDEN reference could collide with external free text (correlation values are 12 characters, ~50 bits). |
| RK-02 Hidden semantic differences | Users may still misread stale SKARVIK snapshots; mitigated by freshness labels and copy only. |
| RK-03 Approval and authorization races | Low: 50-round races (threads and two processes) produced one approval and one authorization each (R07, C-01…C-10). |
| RK-04 Restart recovery | A HALDEN order whose process died before sending stays `UNKNOWN` until a human attests it (by design; absence is not proof). |
| RK-05 Duplicate-order prevention | An audited operations-manager override can still double-book. |
| RK-06 Ambiguous reconciliation | A coincidental full match by an external order with identical account, reference and lines would be accepted (very low likelihood). |
| RK-07 Evidence integrity | A superuser can rewrite the full chain consistently; detectable only against head hashes retained outside the system. |
| RK-08 AI tool misuse | A wrong draft now needs an explicit or confirmed request (a person still submits and another approves); summaries can mislead. |
| RK-10 Reproducibility | Platform differences (L-12). Determinism gate passed on the reference platform: two runs, identical normalized outcomes. |
| RK-12 HALDEN XML via stdlib | Accepted and documented (ADR-F09, L-05). |
| RK-13 HALDEN single ticket | Horizontal scaling is impossible against HALDEN (ADR-F04). |
| RK-14 Simulators built by the author of the adapters | Simulator realism is a fictional approximation; SKARVIK's contract was frozen before the adapter was written. |
| RK-15 OpenAI model/API drift | Observed on two model snapshots only (L-02). |
| RK-16 Dependency churn and CVEs | Audited once (L-01); exact pins and lockfiles; no continuous audit. |
| RK-19 Uncontrolled inference spend | Budgets are reserved before every request; estimates can differ from the invoice. |
| RK-20 Data egress to the inference provider | Only fictional data was sent; a real deployment would need a data-processing review. |

## C. Semantic grounding of assistant answers

| ID | Limitation | Where it matters | Status |
|---|---|---|---|
| G-1 | *Was:* numbers matched as substrings, whole records could be cited, inverted credit-hold statements passed. *Now:* a fact is one field of one result, compared exactly and rendered by the application; summaries and warnings are checked for exact numbers and identifiers, credit-hold direction per account and claims of actions not performed. **Remaining:** the meaning of other free text is not verified; a number attached to another named account, item, system or unit is rejected, but only when the sentence names it and by bounded patterns; hold statements are recognised by English patterns; a customer name alone is not compared. The console labels the summary as the assistant's wording | Reading the summary instead of the facts | Reduced; documented |
| G-2 | Live evidence is larger ([results](evidence/VERIFICATION.md#assistant)) but remains fixed scenarios, one snapshot and one console build | Any statement about reliability | Reduced; documented |
